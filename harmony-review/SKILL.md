# HarmonyOS 代码审查 Skill

> **触发时机**：每次 Harmony 相关代码开发完成后，自动执行本 Skill 对所有变更文件进行审查。
> **依赖**：本 Skill 的审查标准基于 `harmony-develop` Skill 中定义的编码规范。

---

## 一、审查流程

### Step 1：识别变更文件

收集本次开发涉及的所有 `.ets` / `.ts` 文件，确定审查范围。

### Step 2：逐文件按维度审查

对每个文件按以下 6 大维度进行检查（详见第二节）。

### Step 3：判定严重级别

按 P0 / P1 / P2 分级每个问题（详见第三节）。

### Step 4：输出 Review 报告

按统一格式输出审查结果（详见第四节）。

### Step 5：判定是否通过

- ✅ 通过条件：**P0 问题为零** 且 **P1 问题全部解决或有明确计划**
- ❌ 不通过：存在 P0 问题，或 P1 问题未处理

---

## 二、6 大审查维度

### 维度 1：基础风格

| 检查项 | 标准 |
|--------|------|
| 类名、枚举名 | `UpperCamelCase` |
| 变量、方法、参数 | `lowerCamelCase` |
| 常量 | `UPPER_SNAKE_CASE` |
| 布尔值命名 | `is/has/can/should` 前缀 |
| 行宽 | ≤ 120 字符 |
| 缩进 | 统一空格缩进 |
| 引号 | 单引号 |
| 大括号 | 条件/循环必须使用 |
| 函数长度 | 不宜过长（建议 ≤ 50 行） |
| 嵌套深度 | 不宜过深（建议 ≤ 3 层） |

### 维度 2：类型与建模

| 检查项 | 标准 |
|--------|------|
| 公共函数 | 必须声明参数和返回值类型 |
| `any` 使用 | 禁止 |
| `ESObject` 使用 | 禁止 |
| 数组声明 | 优先 `T[]` |
| NaN 判断 | 使用 `Number.isNaN()` |
| 接口 / DTO | 是否有清晰的类型定义 |

### 维度 3：ArkUI 状态使用

| 检查项 | 标准 |
|--------|------|
| `@State` 作用域 | 仅组件内局部状态 |
| `@State` 初始化 | 声明类型 + 本地初始化 |
| 全局数据 | 不应塞进 `@State` |
| 冗余状态 | 只保存源状态，派生数据用计算 |
| `@Prop` vs `@Link` | 子组件入参是否正确区分 |
| 状态数量 | 过多时是否拆了 ViewModel |

### 维度 4：UI 与渲染

| 检查项 | 标准 |
|--------|------|
| `build()` 网络请求 | 禁止 |
| `build()` 复杂计算 | 禁止 sort/filter/reduce 等 |
| `build()` 复杂分支 | 应简化 |
| 页面大小 | 超过 300~400 行应拆分 |
| 组件嵌套 | 超 3 层应拆组件 |
| 长列表 item | 必须组件化 |
| 高频状态刷新 | 是否影响整页 |
| 样式资源化 | 颜色/间距/字号是否主题化 |

### 维度 5：路由

| 检查项 | 标准 |
|--------|------|
| 路由名 | 集中管理，禁止硬编码 |
| 路由封装 | 统一通过 RouterService |
| 参数类型化 | 路由参数有类型定义 |
| 大对象传递 | 禁止（传 ID 代替） |
| 返回链路 | 是否可预测 |

### 维度 6：日志与异常

| 检查项 | 标准 |
|--------|------|
| 日志工具 | 统一使用 Logger |
| 日志分级 | debug/info/warn/error |
| 敏感数据 | 禁止打印 token/手机号/身份证 |
| 吞异常 | 禁止空 catch |
| 用户提示 vs 日志 | 分离 |
| `finally` | 不得 return/break/continue/throw |

## 三、问题严重级别

### P0 — 必须修复（阻断提交）

- 使用了 `any`
- 页面直接写完整业务流程（未分层）
- `build()` 内做网络请求或重计算
- 硬编码路由名、存储 key、文案字符串
- 吞异常（空 catch）
- 打印敏感数据
- `finally` 中 return/throw
- 公共函数无类型声明

### P1 — 必须处理（可附修复计划）

- 未按 feature 分层
- 页面与 ViewModel/Service 未分离
- 可复用组件未抽离
- 状态作用域不清晰
- 公共常量/枚举/资源未统一管理
- 缺少国际化适配（在支持多语言的应用中）

### P2 — 建议优化

- 单文件过长
- 单函数复杂度过高
- 性能风险（整页刷新、未组件化列表项等）
- 测试覆盖不足

## 四、Review 报告输出格式

审查完成后，输出以下格式的报告：

```markdown
# 🔍 Harmony Code Review 报告

## 概览
- 审查文件数：X
- P0 问题：X 个
- P1 问题：X 个
- P2 问题：X 个
- **结论：✅ 通过 / ❌ 不通过**

---

## 详细问题

### 📄 文件：`XxxPage.ets`

| # | 维度 | 级别 | 问题描述 | 建议修复 |
|---|------|------|----------|----------|
| 1 | 类型 | P0 | 第 32 行使用了 `any` 类型 | 替换为 `XxxResponse` 接口 |
| 2 | UI | P1 | `build()` 中调用了 `sort()` | 移至 ViewModel 中预处理 |
| 3 | 风格 | P2 | 文件超过 400 行 | 建议拆分为子组件 |

### 📄 文件：`XxxService.ets`

| # | 维度 | 级别 | 问题描述 | 建议修复 |
|---|------|------|----------|----------|
| 1 | 异常 | P0 | 第 58 行空 catch 块 | 添加 Logger.error 并向上抛出 |

---

## 修复建议汇总

### P0 必须立即修复
1. `XxxPage.ets:32` — 替换 `any` 为具体类型
2. `XxxService.ets:58` — 补充异常处理

### P1 合并前解决
1. `XxxPage.ets` — 将排序逻辑移至 ViewModel

### P2 持续优化
1. `XxxPage.ets` — 考虑拆分为多个组件
```

---

## 五、审查原则

1. **对事不对人** — 审查代码质量，不评价开发者
2. **给出具体修复建议** — 不只说"不好"，要说"怎么改"
3. **优先级明确** — P0 先改，P2 可排期
4. **每次只审查变更部分** — 不翻旧账（除非影响链路）
5. **肯定做得好的地方** — 好的代码也值得被看到

---

## 六、国际化检查

在支持多语言的应用中，额外检查：

- 新增的文本是否使用了 `$r('app.string.xxx')` 资源引用
- 是否存在硬编码的中文/英文字符串
- 是否同步更新了所有语言的资源文件
